## Part 1 — Migration remediation proposal (audit finding X-5)

### 1.1 What is actually broken, precisely

The Alembic chain has 10 files. Reading all of them (not just the ones the
audit already named) confirms **exactly five** are non-functional against a
truly empty database — matching the "five migration files" the user referred
to:

| Revision | File | What's wrong on an empty DB |
|---|---|---|
| `f070db4817a2` | `f070db4817a2_phase_2_models.py` | Root of the chain (`down_revision=None`); `upgrade()` is `pass` — does nothing |
| `cba64ddf4a02` | `cba64ddf4a02_add_confidence_breakdown.py` | `op.add_column('investigation_cases', ...)` — table doesn't exist yet |
| `24d74fa147f3` | `24d74fa147f3_agent_reasoning_engine.py` | Creates `agent_executions`/`agent_reasoning_steps`/`agent_tool_calls` (fine), then runs a **data migration** doing `SELECT ... FROM agent_actions` — table doesn't exist |
| `2331ec567cbb` | `2331ec567cbb_add_cached_metrics_and_explorer_features.py` | `op.add_column` on `agent_executions`/`agent_tool_calls`/`evidence_items` — none exist yet |
| `8532d6f9c999` | `8532d6f9c999_add_investigation_memory.py` | `upgrade()` is `pass` — does nothing (despite the filename) |

**Root cause:** Alembic was adopted onto this project *after* a real schema
already existed (built by `Base.metadata.create_all()` at app startup, before
Alembic was formalized). These five early "migrations" were auto-generated by
diffing a live, already-populated database against the models at each point
in time — they describe real historical schema changes, but none of them
contains the DDL to create the *pre-existing* foundational tables
(`investigation_cases`, `users`, `events`, the old `agent_actions` table,
etc.), because those tables already existed when each migration was
generated. **`alembic upgrade head` has therefore never worked on a genuinely
empty database, from the very first commit that introduced Alembic** — this
is not new damage from the restoration work, it is inherited technical debt.

**What is *not* broken:** every migration from `7a3e8b1d9c4f` onward (5 of the
10 files) is real, coherent, incremental DDL that assumes a complete existing
schema — which is true for every database that has ever actually run this
application, real or dev. **No currently-running installation is at risk from
these five files as they stand today** — they are only unreachable when
starting from revision zero, which is why `scripts/migrate.py`'s workaround
(`create_all` + `stamp head` for an empty DB, `alembic upgrade head` for an
existing one — see Phase 3 restoration log) has been the documented, safe,
supported bootstrap path since 2026-09-17, and remains unaffected by anything
in this proposal.

### 1.2 Why deleting or rewriting them now is the wrong move

1. **Any database currently stamped at exactly one of these five revisions**
   (plausible for any environment — this dev machine, another developer's
   local setup, a staging box — that was bootstrapped before the
   `scripts/migrate.py` fix existed) resolves its upgrade path by walking
   `down_revision` links from `head` back to wherever `alembic_version`
   currently points. Deleting a file in the middle of that chain makes the
   chain unresolvable for that specific database — `alembic upgrade head`
   would raise `Can't locate revision identified by '...'` and the
   installation could not advance at all until manually repaired.
2. **Rewriting a file's DDL after it may have already run** is worse than
   deleting it: Alembic has no way to know the content changed, so a database
   that already applied the old version silently diverges from one that
   applies the edited version, with no error raised anywhere.
3. Squashing (replacing all five with one collapsed file, same revision IDs)
   has the same problem as deleting for anything not stamped at exactly the
   old head of the squashed range.

None of this is theoretical risk-aversion for its own sake: it is the direct,
predictable consequence of Alembic's linear revision-chain design, and it is
exactly why the user's instruction to not touch these files yet is the
correct default until a squash/rewrite is proven safe for every real
database that might exist.

### 1.3 The proposed fix: insert one new file, change one line — nothing else

Alembic already has a standard, well-understood pattern for exactly this
situation (adopting version control after a live schema exists): insert a new
**genesis migration** *before* the current root, containing the DDL for the
schema as it existed at that point, and repoint the old root's
`down_revision` at it.

**Concretely:**

1. Add one new file, e.g. `alembic/versions/000000000001_genesis_baseline.py`,
   with `revision = "000000000001"`, `down_revision = None`, whose `upgrade()`
   creates every table the five broken migrations assume already exists
   (`investigation_cases`, `users`, `events`, `evidence_items`,
   `attack_techniques`, `security_entities`, `security_relationships`,
   `replay_sessions`, and the now-long-dropped `agent_actions` table so that
   `24d74fa147f3`'s `SELECT ... FROM agent_actions` succeeds — returning zero
   rows on a fresh install, which is correct).
2. Change exactly one line: `f070db4817a2`'s `down_revision` from `None` to
   `"000000000001"`.
3. Nothing else changes. All 10 existing files keep their current content,
   their current revision IDs, and their current relative order.

**Why this is safe for every existing installation, not just new ones:**
Alembic determines what to run by walking backward from `head` through
`down_revision` links until it reaches the database's *currently stamped*
revision — it only applies migrations it finds *between* that point and
`head`. A database already stamped at `f070db4817a2` or later never sees the
new genesis migration in that walk at all, because the genesis migration is
now an ancestor of a point the database has already passed, not something
between "where it is" and "head". This is the standard, textbook-safe way to
retrofit a genesis migration into an existing chain; it is not a workaround
specific to this codebase.

**This already has real supporting evidence, not a hypothesis:**
`backend/tests/support/baseline_schema.py`'s `create_baseline_schema()`
already contains almost exactly this DDL (the schema as of `7a3e8b1d9c4f`,
one step further along than where the proposed genesis migration would sit),
and `backend/tests/test_migrations.py::test_migrations_upgrade_baseline_to_model_schema`
already proves, on a real Postgres database, that "create this baseline
schema → stamp `7a3e8b1d9c4f` → `alembic upgrade head`" produces a schema
with **zero diffs** against the live ORM models (`compare_metadata(...) ==
[]`). The proposed genesis migration would sit one step earlier (before the
five broken files, not after them) and would need to additionally create the
long-dropped `agent_actions` table so `24d74fa147f3`'s data-migration `SELECT`
succeeds — everything else can be adapted directly from the already-tested
`create_baseline_schema()` content.

### 1.4 What is explicitly *not* proposed

- **Not** deleting any of the five files.
- **Not** rewriting any of the five files' `upgrade()`/`downgrade()` bodies.
- **Not** changing `scripts/migrate.py`'s current behavior. Once the genesis
  migration is implemented and verified, `scripts/migrate.py`'s `create_all`
  branch for empty databases *could* eventually be simplified to a plain
  `alembic upgrade head` for every case — but that is an optional future
  simplification, not a requirement, and should only be considered after the
  genesis migration itself has been running safely for some time.
- **Not** implementing any of this in the current session. This is a
  proposal for a **future, separate phase**, to be implemented and tested on
  its own, specifically because it touches the migration chain — the one
  category of change where a mistake is hardest to reverse for anyone
  already running the application.

### 1.5 Verification plan for when this is implemented (not run now)

1. `alembic upgrade head` from a genuinely empty database (drop and recreate
   it first) must now succeed end to end, with no `scripts/migrate.py`
   involvement, producing zero `compare_metadata` diffs against `Base.metadata`
   — this is the concrete, currently-failing case from the Phase 0-9
   verification checkpoint (`docs/YAROX_REALITY_AUDIT.md`), and becomes the
   regression test proving the fix.
2. Simulate every one of the five old stamp points (`f070db4817a2`,
   `cba64ddf4a02`, `24d74fa147f3`, `2331ec567cbb`, `8532d6f9c999`) on a
   database built via the *old* `create_baseline_schema()`-style DDL (i.e. as
   if that installation predates this fix), stamp it there, then run
   `alembic upgrade head` and confirm it reaches head cleanly with no attempt
   to re-run the genesis migration.
3. Confirm `scripts/migrate.py`'s existing "already-versioned DB" branch
   (`alembic upgrade head`) is unaffected for a database already at the
   current real head (`e5f6a7b8c9d0` or later by the time this ships).
4. Re-run the full backend test suite and the fresh-database verification
   procedure already established in the Phase 0-9 checkpoint.

## Part 2 — Dev-data inventory & backup plan (audit finding X-7)

### 2.1 What's actually in the dev database right now

Queried live against the running dev Postgres (`yarox` database) and Qdrant,
2026-09-19:

| Table | Rows |
|---|---|
| `users` | 27 |
| `investigation_cases` | 95 |
| `events` | 290 |
| `investigation_memory` | 8 |
| `audit_logs` | 2 |
| `case_notes` | 0 |
| `agent_executions` | 513 |

Qdrant: `investigation_memory` collection has 8 points (matches the 8
`investigation_memory` rows exactly — no orphans currently, consistent with
the Phase 4 `reconcile` cleanup already recorded in the audit log). A second,
apparently-unused collection named `investigations` exists with 0 points —
worth a separate, low-priority cleanup decision, not part of this proposal.

**Users, precisely:** 3 are the genuine seeded accounts
(`admin@yarox.local`, `analyst@yarox.local`, `viewer@yarox.local`, created
2026-08-22 11:36:05 — matching `seed_initial_users()` at app startup). The
other 24 are auto-generated accounts with random hex suffixes
(`admin_7f0581@yarox.local`, etc.), all created within an ~80-second window
on 2026-08-23 18:51-18:52 — clearly a pre-isolation automated test run
(predating the Phase 1 test-isolation fix, 2026-09-17, which now prevents
tests from ever writing to this database at all — verified in the Phase 1
restoration log).

**Cases, precisely:** case *titles* are not distinguishably "fake" — they are
genuine detection-engine output (`"Brute Force"`, `"Command and Scripting
Interpreter"`, etc.), because they were produced by real replay/test runs
before test isolation existed, not by hand-typed placeholder data. The
distinguishing signal is timing, not content: 79 of 95 cases (83%) were
created in a single 3-day burst, 2026-08-21 through 2026-08-23 — before
isolation — versus a trickle of 1-5 cases per day from 2026-09-05 onward,
which includes this restoration project's own legitimate verification runs
(Phases 0-11 live-verification replays, including several run earlier in
*this* session). **Any purge must not simply cut by date** — some post-08-23
cases are this project's own recent verification evidence, referenced by
exact ID in `docs/YAROX_REALITY_AUDIT.md`'s restoration log entries, and
deleting them would make that log's evidence unverifiable after the fact.

### 2.2 Backup plan (to run before any purge, not run now)

```bash
# 1. Full Postgres dump (dev DB is currently 12 MB — trivial to store)
docker compose exec -T postgres pg_dump -U yarox -d yarox -Fc \
  > backups/yarox_dev_$(date +%Y%m%d_%H%M%S).pgdump

# 2. Qdrant snapshot (both collections; the API returns a snapshot name to download)
curl -s -X POST http://localhost:6333/collections/investigation_memory/snapshots
curl -s -X POST http://localhost:6333/collections/investigations/snapshots
# then download each named snapshot via GET .../snapshots/{name} and store alongside the pg dump

# 3. Verify the dump restores cleanly into a throwaway database before trusting it
docker compose exec -T postgres createdb -U yarox yarox_backup_verify
docker compose exec -T postgres pg_restore -U yarox -d yarox_backup_verify \
  /path/to/the/dump/inside/the/container
docker compose exec -T postgres psql -U yarox -d yarox_backup_verify -c "SELECT count(*) FROM investigation_cases;"
docker compose exec -T postgres dropdb -U yarox yarox_backup_verify
```

Both `pg_dump`/`pg_restore` (already the pattern used for the fresh-database
verification in the Phase 0-9 checkpoint) and Qdrant's snapshot API are
already-available, standard tooling — no new infrastructure needed.

### 2.3 Proposed purge criteria (not executed — for review)

Rather than a blanket date cut, the precise, defensible criterion is: **purge
the 24 non-seeded users created in the 2026-08-23 18:51-18:52 burst, and any
case/event/evidence/memory row that traces back to one of those users or was
created in the 2026-08-21–23 window AND is not cited by exact ID in
`docs/YAROX_REALITY_AUDIT.md`'s restoration log.** This preserves every piece
of data this project's own documentation points to as evidence, while
removing the actual pre-isolation contamination. This still needs an explicit
go-ahead before running, and should run against a **freshly verified backup**
per 2.2, not the live dev database directly.
